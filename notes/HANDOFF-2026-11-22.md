# QuotaVPN 0.7.0 migration handoff, 22 November 2026

This is the state of the Windows credential migration after the implementation pass. It replaces
the optimistic status lines in `QuotaVPN_0.7.0_Handoff.md` where they disagree with the checkout.

## What the Windows app does now

- A card arrives as two lines from the provider: `qc1:<uuid>:<64 hex secret>` and the matching
  `vless://` link. The app matches them by canonical UUID and refuses a mismatch.
- The secret is stored in `%APPDATA%/quotacards/card_credentials.bin`, one DPAPI-sealed JSON map
  keyed by card UUID. Importing a second card does not overwrite the first. The file is written
  through a temporary file and replaced, and the plaintext secret never reaches disk.
- Every card-management call is an HTTPS POST signed with HMAC-SHA256 over
  `op\nuuid\nts\nnonce`. The endpoints are `/v1/register`, `/v1/revoke` and `/v1/status`. The body
  is `{op, uuid, ts, nonce, sig}`. TLS is verified through `reqwest` with rustls; the old
  `curl -k` is gone, and the body is not a command-line argument.
- No card UUID is minted in the app any more. The provider issues cards. If a user has no card of
  the selected kind, the UI opens the import dialog instead of creating one.
- `probe_server` is gone. It used to add and revoke a throwaway client on every connect, which
  restarted Xray twice per connect. The new status command is read-only.
- On a tunnel failure the app may call `register` once for the active card, but only when the card
  has an imported credential. A card with no credential reports that instead of a generic 403.
- Removing a card in the app is local only: the credential and the local card are deleted, and the
  server entry is left for the owner to revoke with `qc-provision revoke`. The UI says so.
- `initial_config` clears the old SSH key and the old plaintext `device_secret` from the profile.
  The desktop no longer writes a keypair and no longer needs `EMBED_KEY`; `build.rs` writes
  `EMBED_KEY = None` for every build.

## What was removed or gated

- `src/server.rs` and `src/ssh.rs` are behind the `legacy-ssh` Cargo feature. The desktop depends
  on `quotacards` with `default-features = false`, so `russh`, `russh-keys`, `ssh-key` and their
  PEM parser constants do not enter the Windows binary. The phone still uses the default feature
  and the old SSH path until its own migration.
- The desktop's `server::*` calls are gone: probe, launch heal, card creation, card import, revoke,
  Hysteria2 password fetch, AWG parameter fetch, WireGuard peer add and server public key fetch.
- A newly imported card is VLESS only. Hysteria2 and WireGuard still work for a card that already
  has cached `hy2_password`, `awg_params`, `wg_server_pub`, `wg_private` and `wg_addr` in
  `config.json`. There is no SSH fallback when they are missing; the UI says the card has no
  profile for that transport.

## What the UI has

- A `Card credential` row in Settings, with the active card, whether a management credential is
  imported, `Import credential`, `Check status`, and a two-step `Forget card`.
- `CardImportDialog` accepts both lines in one paste. It reads the SNI from the `vless://` link and
  switches the Gamerz/Streamerz choice automatically; the switch stays available when only the
  `qc1:` line is pasted.
- The Home preset buttons, the one-tap connect flow and the domain picker open the import dialog
  when no card of that kind exists.
- EN and AR strings are in `src/lib/i18n/{en,ar}.ts`. Arabic changes text direction only.

## Blockers and things not verified

1. **The DNS name moved to `quotavpn.duckdns.org`.** It resolves to `80.225.89.162` from the local
   resolver and Cloudflare DoH. The old `quotacards.duckdns.org` is NXDOMAIN. The desktop rewrites
   an old default host on launch; old `vless://` links that still carry the old name will not
   resolve and need to be reissued.
2. **TCP 443 answers, TCP 8444 still times out.** The OCI ingress rule is now the blocker. The API
   certificate must be reissued for `quotavpn.duckdns.org` because the client verifies TLS. The
   tunnel on 443 keeps its self-signed `ea.com` certificate and `allowInsecure`, so it is not
   affected.
3. **The server-side API and helper are not in this repository.** The live source of
   `qc-provision`, `qc-xray-client`, the API app, its systemd units and `devices.json` was not
   available, so the HMAC canonicalisation, endpoint paths, rate limits, nonce persistence,
   file permissions and systemd sandbox could not be checked against this client. The client
   follows the handoff contract; it has not been proven against the live service.
4. **Android is held at 0.6.18.** The shared crate now compiles for Android again (the core
   `qcreg` is pure), but the phone still uses the SSH path and the old `EMBED_KEY`. Do not ship a
   0.7.0 APK: there is no Android credential store, no phone import UI, and the old PEM is gone
   from the tree. A 0.7.0 Windows-only release is a deliberate exception to the usual same-version
   rule.
5. **Existing customers** keep their UUIDs and cards in `config.json`. They can still connect over
   VLESS without importing a credential. To gain self-repair and status, the owner must run
   `qc-provision issue <uuid>` for each card and deliver the `qc1:` line plus the existing vless
   link. Importing a card that is already registered only calls status; it does not restart Xray.
   A new card that the server does not know gets one register call, which does restart Xray once.
6. **Card revoke from the app is not wired.** The API client has the `revoke` path, but the UI
   only forgets locally. The owner revokes with `qc-provision revoke`.
7. **The build stamp is `dev`** in the local MSVC artifact because the build machine's build script
   captured a previous run without Git on PATH. The CI build from a clean commit is the one that
   must carry the short hash. Do not publish this local artifact.

## Network page, 0.7.1

The Network page is back, rebuilt around passive discovery and explicit
one-device control. The old page watched every device and that is gone.

- **Why the old watch took the network down.** `windivert.rs` used layer `2`
  (`WINDIVERT_LAYER_FLOW`) for the forward pass. `WinDivertOpen` correctly
  answered `ERROR_INVALID_PARAMETER` (87), but the code only checked for a null
  handle. `WinDivertOpen` returns `INVALID_HANDLE_VALUE` on failure, so the
  error was accepted as a live pass, the ARP claim still went out, and the
  device was pointed at a PC that never forwarded a packet. Layer 1
  (`WINDIVERT_LAYER_NETWORK_FORWARD`) is the forward layer. `open_forward` now
  rejects both null and `INVALID_HANDLE_VALUE` and names the OS error.
- **Why a released session left a process.** The stop thread only wrote a flag,
  while the pump was blocked in `WinDivertRecv`. The thread now calls
  `WinDivertShutdown` on the same handle (held in an `Arc`), so release wakes
  the receive, the pump exits, the policy file is removed and the ARP claim
  loop sends the restore frames. `start_with` also waits for the pass to publish
  `running:true` before claiming; if it fails it returns the driver's own error
  and claims nothing.
- **One device at a time.** `lan_monitor_start` is retired and returns an error.
  The page only calls `lan_start` for the selected device. Caps and blocks are
  written to `lan/policy.json`; the policy units are KB/s and the pump stores
  bytes/s. The page sends KB/s directly and shows the same value back.
- **Names.** The roster hides every name until the router session is live. A
  name with source `router` is shown only while `router_linked` is true. The
  login dialog sends the credentials once; `router_remember` is cleared at
  startup and `router_link` no longer saves anything. `scan_with_router` merges
  the router's full client table, including phones the sweep cannot wake.
- **Npcap.** The free installer has no silent switch; `/S` answers "Silent
  installation is only supported in Npcap OEM". `install_npcap` now runs the
  normal wizard (I Agree, Finish) and waits. The page explains that a window
  will open. Npcap and WinDivert are both required before the page enables
  Take control; Npcap is downloaded from npcap.com and its Authenticode
  signature is checked. WinDivert ships beside the exe and is copied into the
  engine folder by `lan_prepare`.
- **UI.** New page in `desktop/ui-next/src/screens/Network.tsx`: router strip,
  searchable roster with IP/MAC/name and copy buttons, and a focus panel for
  one device with download/upload caps, block/unblock and Release. Names show
  "Unknown device" with "Sign in to name" until the router login. The guard
  alert only renders for a valid, foreign MAC; the guard could otherwise call
  the router or our own claim an attacker.
- **Verified.** On this PC: Npcap 1.90 installed from the vendor installer,
  service `npcap` running; 64 KB/s down and 32 KB/s up reached
  `policy.json` as `down_bps: 65536`, `up_bps: 32768`; block and unblock
  toggled `blocked`; Release set `running:false`, removed the policy, stopped
  the pipeline process and restored the device's ARP entry. A real video call
  or stream through a capped device is still the one test to run.
- **Private installer.** `desktop/src-tauri/target/release/bundle/nsis/QuotaVPN_0.7.1_x64-setup.exe`
  (5.53 MB, updater artifacts off, unsigned) includes WinDivert again because
  the control page needs it. Defender scanned it clean. Not published. This
  build is superseded below: the relay build has no WinDivert and is 5.43 MB.

### Update, 23 November: local control rebuilt as a layer-2 relay

The 0.7.1 forward pipeline never carried anything on this PC: Windows had
`Forwarding: disabled` on the Ethernet interface and `IPEnableRouter=0`, so a
claimed device's packets arrived at the PC and were dropped. The claim still
went out, which is why selecting the phone and playing a video took it offline.
That path is retired.

- **How it works now.** `src/lan_relay.rs` opens Npcap non-promiscuous on the
  wired adapter and owns the whole session in the app process. It tells the
  device the gateway is the PC, tells the router the device is the PC, and
  re-addresses frames in both directions at layer 2. The PC's IP stack, routes,
  firewall and VPN never see the device's packets, so there is no forwarding to
  switch on and the PC's own connection cannot be pulled into the path.
- **Safety.** The capture opens first; a broadcast ARP probe asks who holds the
  device's IP and learns its current hardware address; only then are the claims
  sent. A failed probe or a failed first send changes nothing. Every exit,
  including a panic, sends the true mappings back, and the existing journal
  restores a session whose process was killed.
- **The PC's own gateway is pinned.** Before the first claim, the app makes the
  PC's neighbour entry for the router Permanent with the router's real hardware
  address (`New-NetNeighbor -State Permanent`, recorded in `lan_pin.txt`). ARP
  replies can no longer rewrite the PC's way to the router, which is what took
  the PC's own connection down during a session. A watchdog re-pins it every
  two seconds and ends the session if it cannot; release removes the entry.
  If Windows refuses the pin, nothing is claimed.
- **The roster is tidied before it is painted.** `lan::tidy_roster` forces the
  gateway row to the router's real address and this PC's row to its own, and
  drops any other row wearing either address before the identity pass. Without
  it a poisoned cache put the PC's MAC on the router and on the phone, which
  also gave several rows the same React key and duplicated the list. The page
  key is now `ip|mac|self`, so even a bad row cannot collide.
- **The upload half now works when the device accepts the claim.** A targeted
  ARP reply alone was ignored by the 2514. The relay also sends a gratuitous
  reply and a gratuitous request to the device; one of those moves the gateway
  entry. On 24 Nov the 2514 at `192.168.1.23` carried 175,733 B up and
  7,865,387 B down in 30 s with 0 drops, while the PC stayed pinned to the
  router. A device that ignores all three forms still sends uploads directly;
  the page detects `up_bytes == 0` and disables the upload field with an
  explanation, and the router's QoS is the remaining path for it.
- **Measured on this PC (23 Nov).** Phone `192.168.1.28`, 40 s uncapped video:
  22,642,184 B down, 17,607 frames forwarded, 0 dropped, 0 up (the pinned
  gateway). A 20 s run at 96 KB/s down: 569,911 B carried, 261 forwarded, 200
  dropped, so the cap bites. A 30 s phone session after the gateway pin and the
  roster tidy: the router entry stayed `Permanent` on
  `f0:a9:51:c1:eb:da`, the PC's HTTPS answered at every 3 s check, the roster
  read one row each for the PC, router, phone and the two other devices with
  their real MACs, and the phone answered 5/5 pings after release.
- **What ships.** WinDivert is no longer bundled or used for control;
  `tauri.conf.json` has no driver resources and `lan_prepare` only reports
  Npcap. The 0.7.1 installer at
  `desktop/src-tauri/target/release/bundle/nsis/QuotaVPN_0.7.1_x64-setup.exe`
  (5.43 MB, unsigned, updater artifacts off) is rebuilt and installed locally.
  Still private; nothing published.
