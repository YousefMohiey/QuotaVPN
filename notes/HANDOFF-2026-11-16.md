# Handoff: what changed, 2026-11-14 to 2026-11-16

For whoever picks this up on a Windows machine. Everything below was done in one
long session that started at Step 1 of the LAN work and ended at v0.6.17. Read the
"Where your PC is" section first, then "Current architecture", then "Open problems".

The security audit that drove a large part of this is in
`notes/SECURITY-AUDIT-2026-11-15.md`.

Releases between 0.6.6 and 0.6.9 are broken on purpose as a record: 0.6.6 had no

0.6.8 installed persistence from the installer. Do not rebuild from those tags.
v0.6.10 and v0.6.11 were published and then deleted, tags included.

## Where your PC is

Your copy is older than all of this. On Windows:

```
git pull
# version files must agree; check all four
grep -h '"version"' desktop/src-tauri/tauri.conf.json
npm --prefix desktop/ui-next ci
npm --prefix desktop/ui-next run build
cargo test                      # expect 55 passing
cd desktop && npx @tauri-apps/cli@2 build
```

The built installer lands in `desktop/src-tauri/target/release/bundle/nsis/`.
Two things will bite you:

1. **`installMode` is `perMachine` now** (0.6.12). Installs go to Program Files, not
   the user profile. Upgrading in place across that change leaves two copies: uninstall
   the old one first.
2. **`embed/quotacards-embed.pem` is gitignored and absent.** A build made from a
   checkout has no device key, so `EMBED_KEY` is `None` and the app will not be
   zero-setup: it has no server address and no key the server trusts. Builds made on
   the machine that holds that pem are the only zero-setup builds. `build.rs` also
   accepts it from `QC_EMBED_PEM`, which is how a CI build could carry it.

## What happened, in order

### 1. Device-only mode (Step 1), commit `2e530cb`

A routed LAN device's traffic rides the tunnel while the PC itself stays direct.
`strict_route` is `route_final != "direct"`, device rules land at index 4 of the
sing-box config (after the rejects, before the DNS hijack), and `direct` outbound pins
both `inet4_bind_address` and `bind_interface`. The config refuses to build
device-only with nothing to bind.

### 2. LAN stack moved off Npcap, commits `33c4723`, `b08f21f`, `d12f903`

The watcher, limiter, blocker and device discovery were rewritten onto WinDivert's
forward layer plus native discovery:

- `src/windivert.rs` (new): driver loader, `Divert`, filter building, DNS/TLS-SNI/HTTP-Host
  parsing, `pace`, driver install.
- `src/lan_forward.rs` (new): the elevated packet loop, `policy.json` in, `state.json` out.
- `src/lan_ctrl.rs`: rewritten to drive the loop through the policy file; the legacy
  pcap capture loops are deleted.
- `src/lan_ask.rs`: plain `UdpSocket` instead of pcap.
- `src/dhcp_names.rs`: rewritten; opportunistic UDP:67 listener.
- `src/wpcap.rs`: `ClaimLink` trait with two backends, `GatewayMode` and
  `NpcapClaimFallback` (dynamic `wpcap.dll`).

### 3. Silent pipeline and UI readiness, commits `0d6e974`, `0e6234f`

The pipeline starts through the elevated helper task, like the tunnel, so it costs no
prompt. `ui-next` asks `lan_claim_ready` instead of "is Npcap installed".

### 4. The release loop and three Defender verdicts, 0.6.6 to 0.6.9

Published 0.6.6 (would not start), 0.6.7 (quarantined for carrying the driver),
0.6.8 (quarantined for installing persistence), 0.6.9. Fixes along the way:
tauri-build embeds the manifest (there was no manifest at all in the MSVC build), the
driver left the package, and the installer stopped spawning a hidden elevated setup.

### 5. The server-setting detour, commits `46ff9ea`, `6c9503e`, then reverted

0.6.9 could not connect at all: every connect answered "Set up your server first". The
cause was that `embed/quotacards-embed.pem` is gitignored, so a CI build bakes in
`EMBED_KEY: None`, and the only code that fills an empty `server_ip` sits behind
`if let Some(embedded)`. I added a Settings screen with a server address field and a
public-key display, shipped it as 0.6.10 and 0.6.11, and the owner rejected it: a VPN
client should not display credentials. Both releases were deleted, tags included, and
the tree was reverted to 0.6.9. **Do not reintroduce a key display.** If an install
needs a server, the answer is the embedded key at build time.

### 6. Security audit, commit `4ab5f6b` onwards

Four parallel reviews (secrets/supply chain, network, LAN/elevated, local surface)
against `edd1f84`. Full report in `notes/SECURITY-AUDIT-2026-11-15.md`. Fixes:

- `src/windivert.rs`, `src/vpn.rs`: every downloaded artifact is pinned by SHA-256 and
  verified before it is extracted or loaded. Engine, Wintun, Ookla, and the WinDivert
  pair. The DLL hash is checked **before** `LoadLibrary`, because a DLL's initialiser
  runs inside the load.
- `src/ssh.rs`: SSH host keys are pinned, trust on first use, stored in
  `ssh_host_key.txt` next to the config. It used to answer `Ok(true)` to every key.
- `src/server.rs`: the card id is validated unconditionally before it is substituted
  into a script run as root on the server.
- `desktop/src-tauri/src/lib.rs`: `open_page` accepts only URL-shaped text (it went to
  `cmd /C start`, so `https://x&calc.exe` executed); `app_icons` no longer accepts a
  path from the page.
- `src/lan_route.rs`: the recovery record must match the live neighbour table before
  it forges ARP frames.
- `src/lan_forward.rs`: policy addresses are parsed as IPv4, lists capped, session TTL
  bounded.
- `src/dhcp_names.rs`: names bounded and stamped (see 0.6.17 below).
- `src/vpn.rs`: the elevated uninstall script goes as an encoded command, not a file.
- `nsis-hooks.nsh`: uninstall always removes the helper tasks; the keeper marker is gone.
- CI: signing secrets scoped to their steps, CLI pinned, `--clobber` removed,
  `persist-credentials: false`.

### 7. Antivirus chase, 0.6.13 to 0.6.16

- 0.6.13 removed the WinDivert download and install, removed the SmartScreen disable
  from the WebView arguments, and removed `QC_FEED_URL`. Verified by CI assertions on
  the shipped binary, not by `strings` on the installer: NSIS compresses its payload,
  so a `strings` check of the setup file proves nothing.
- 0.6.14 moved helper registration into the installer. **Wrong**: Defender answered
  `Behavior:Win32/Persistence.A!ml`, naming
  `C:\Windows\System32\Tasks\QuotaVPN Network $USERNAME`. Registering a scheduled task
  whose action launches the executable is the detected behaviour, regardless of the
  token, and `$USERNAME` is not an NSIS variable so the name carried the literal text.
- 0.6.15 moved the feed to the raw URL (answers 200, no redirect) and made a failed
  update check report its real reason instead of the canned "Could not reach GitHub".
- 0.6.16 removed scheduled tasks entirely. The engine and the LAN pipeline are
  detached children of the app, which already holds an administrator token.
  `install_*_task` are now cleanup functions that delete tasks left by older versions.

### 8. Network screen, 0.6.17

- Device names were wrong because the DHCP cache stored `mac|name` with no time: one
  bad announcement was permanent. Entries are `mac|name|unix`, trusted for 24 hours;
  the old untimed form is dropped on upgrade.
- `GatewayMode::send_claim` answered `true` without sending a frame, so a route could be
  reported as working when nothing left the machine. It answers false and `claim`
  refuses with a sentence naming the missing packet driver.
- The router sign-in is gone: the card, the dialog, and the silent auto-link in the poll.

## Current architecture

**Elevation.** The app manifest requests `requireAdministrator`, so the window, the
IPC commands and the WebView host all run elevated. The install is per-machine, so the
executable lives in Program Files and a normal user cannot replace it.

**Processes.** The engine (`--run-engine`) and the LAN pipeline (`--lan-pipeline`) are
spawned as detached children with `DETACHED_PROCESS | CREATE_NEW_PROCESS_GROUP`. The
engine writes its pid to `engine.pid`; `task_engine_pid` reads that, with a `tasklist`
fallback. Nothing is registered with the Task Scheduler.

**Packet access.**

| feature | needs | state today |
|---|---|---|
| device discovery, names | nothing (UDP sweep + ARP table + DHCP/mDNS probes) | works |
| route a device through the tunnel | Npcap (`wpcap.dll`) to send ARP replies | works once Npcap is installed |
| watch / limit / block | WinDivert forward layer | **does not work**, the driver is not installed by the app |

Npcap is installed by its own signed installer, from the button on the Network screen.
`lan_route::install_npcap` still downloads and executes it; that path is on the
security list below.

**Files.** Engine dir is `%LOCALAPPDATA%\quotacards\engine`. Config is
`%APPDATA%\quotacards\config.json`. LAN wire protocol is `engine\lan\policy.json` in,
`engine\lan\state.json` out, `engine\lan\stop` to stop.

## Open problems, by value

1. **Limit and block do not work at all.** They are forward-layer features: they filter
   packets this PC forwards. Npcap can copy packets, not drop or pace them, so the only
   route is WinDivert, and the app no longer installs it. Decide: (a) leave them off,
   (b) ship/fetch WinDivert again with the hash pins already in place and accept the
   antivirus risk that quarantined 0.6.7, or (c) reimplement blocking as "claim the
   device and stop forwarding", which Npcap can do, and drop rate limiting.
2. **TLS verification is still disabled on both transports** (`src/vpn.rs:762`, `:818`,
   `"insecure": true`). The server certificate is self-signed for ten years with CN
   `ea.com` and nothing pins it. This cannot be fixed client-side alone: the server has
   to expose a certificate to pin.
3. **The Npcap installer path is still download-and-execute.** `lan_route.rs:432`
   fetches to `%TEMP%`, verifies the vendor signature, then runs it. Same TOCTOU shape
   the audit flagged elsewhere, and it now also runs elevated because the app is.
4. **No code signing.** SmartScreen warns on every install, and heuristic engines may
   quarantine. `notes/defender.md` has the history.
5. **Zero-setup is gone for CI builds** (no embed key). Either build on the machine
   with the pem, or set the `QC_EMBED_PEM` secret and wire it into the workflow's build
   step env.
6. **The repository's `qc-agent` does not match the live one.** It rejects the commands
   the client actually sends (`embed/qc-net.sh:203-218`), so the deployed agent is
   different code. Nothing about the per-device secret can be trusted until that is
   reconciled.
7. **Update feed rollback**: `latest.json` is unsigned and its `version` is trusted, so
   a forged feed can point at an older signed installer.
8. `res/windivert/*` is still committed (dev only, not bundled). It is unused by the
   install path now; keep it for `cargo tauri dev` or delete it.

## Build and release, from Windows

1. Bump all four files together to the same version:
   `desktop/src-tauri/Cargo.toml`, `desktop/src-tauri/tauri.conf.json`,
   `android/tauri-app/src-tauri/Cargo.toml`, `android/tauri-app/src-tauri/tauri.conf.json`.
2. `cargo test` (expect 55+) and `npm --prefix desktop/ui-next run build`.
3. Commit, `git push origin master`, then `git tag -a vX.Y.Z -m "..." HEAD` and push the tag.
4. `.github/workflows/signed-release.yml` builds on the tag. It uploads three artifacts:
   the installer, its `.sig`, and `QuotaVPN.exe`. It fails the build if the binary
   contains the driver URL, `QC_FEED_URL`, `<Task version=` or `schtasks /Create`, and if
   `additionalBrowserArgs` disables SmartScreen.
5. Download the artifacts with `gh api .../artifacts/<id>/zip` (`gh run download` fails
   on `archive: false` artifacts).
6. Compose `latest.json` by hand: `version`, `build` (short hash), `notes`, `pub_date`,
   `platforms.windows-x86_64.{signature,url}`.
7. `gh release create vX.Y.Z --notes-file ... installer .sig latest.json`.
8. Commit the updated `latest.json` to `master` and push: that is the file the app
   actually reads first. The release asset is the fallback endpoint.

There is no signing step. The header of the workflow says so.

## Things that will look like bugs and are not

- The app says "Could not reach GitHub" only if the check fails on both endpoints; the
  real reason is in `singbox.log` under the engine directory.
- A fresh install with no server and no device key shows "Set up your server first" and
  that is correct for a checkout build.
- The router card and the "Router" filter are gone from the Network screen on purpose.
- `task_installed()` and `lan_task_installed()` return `true` by design: there is
  nothing to install.
